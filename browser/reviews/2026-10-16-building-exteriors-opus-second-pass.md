## Measured code defects

**1. Medium: gates 35/246 can seal a passage the game treats as real.** The north-entrance check in `gate-building-shells.ts:100` skips any warp without a direction (`passageOnly`). Every other family treats such a warp as a passage and backs off (for example `facility-building-shells.ts:66`, `landmark-building-shells.ts:160`, `misc-building-shells.ts:160-162`), as does the generic pass. The exporter marks these exits on purpose so a rear wall can't close them (`export_entrances.py:23-25`). In the gate's closed branch, `finish` hides the generic closure (`:34`) and builds a solid rear wall (`:56-57`). Directional warps north of z=-96 are also ignored. No gate test covers either case. I can't confirm a real map hits this without the entrance data.

**2. Medium: one family exception takes down the whole warp.** `world.ts:142` calls `closeBuildingExterior` with no try/catch or fallback to the generic repair. A throw rejects the prop, which is rethrown into the cell job (`:142`), then into `pending` (`:147`), and `enter()` fails. The builders contain unguarded non-null assertions, for example `house-building-shells.ts:95` (`find(...)!`, used on `:96`) and every `getBarycoord(...)!` sampler. Nothing shows a current asset throwing, but any unexpected asset variant becomes a failed warp instead of a fallback.

**3. Medium: shell generation runs synchronously with no frame budget.** Each prop's generic and family generation runs in a promise continuation (`world.ts:142`). When assets and entrances are already cached, a cell's props can run back to back with no yield to rendering. The stale-generation check only happens after all props are built (`:143`), so superseded streams still pay the full cost. The audit's timings are Node wall-clock and say themselves they aren't browser frame times (`audit_building_enclosures.ts:630`). Whether this actually causes hitches is unmeasured.

**4. Low: shells read hidden template meshes and, in some families, instanced meshes.** The generic pass (`render-repair.ts:117`) and every family's face collector (for example `house-building-shells.ts:12`) use `traverse`, not `traverseVisible`. The template repair hides originals and adds replacements, so a mesh that was only partly replaced can be read twice. That would break the "edge used once" boundary logic (`house-building-shells.ts:103,197`, `station-building-shells.ts:83`). The generic pass, gate (`:12`), pokeathlon (`:12`) and special (`:11`) also read instanced meshes but ignore each instance's position. A fence's unit box would then sit at the model origin and could pull the generic pass's minimum height down. This only matters if a building model embeds fence or rock cards, which I haven't verified.

## Unverified visual or numerical hypotheses
- Almost every family's `finish` hides every generic `3d-solid-backing` and `3d-rear-facade` in the model (for example `house-building-shells.ts:237`). Small separate parts in the same model, like signs, may lose their added thickness.
- Rear-door detection only looks at −Z. A house with a side door in the front half would get a `house-side-closure` panel across it (`:61`, `:215`).
- Shrine accepts a rear door only if it is strictly less than 8 units from the rear wall (`shrine-building-shells.ts:32`). Warp positions are tile centres, half a tile (8 units) in from the tile edge, so a rear door can land exactly on that boundary.
- Footings are built from every visible edge at floor level, so each generated wall layer gets its own nearly coplanar footing strip. That could flicker where a strip lacks the depth offset.

## Validation limits and claims that go beyond their checks
- The dispatcher tests always pass no doors (`building-exterior.test.ts:29,39,48`). That turns the generic pass off entirely (`render-repair.ts:116`), so the real runtime order is never exercised with entrances.
- That same test exempts 1-9-86, 1-147-9 and 1-263-90 from creating owned resources (`:43`). So whether the arch and castle hull removal (147/263) happens on runtime-placed clones is never asserted. The transformed castle test checks one ray, not `removedHullFaces` (`frontier-building-shells.test.ts:48`).
- No world or streaming test covers the `world.ts:142` integration.
- `building-exterior.ts:27-28` says the gallery, audit and game share the exact repair order. The gallery (`building-gallery.ts:32`) and enclosure audit (`:399`) have no terrain offset or footings. The footing audit only checks for finite values and timing (`audit_building_footings.ts:21-22`). The footing unit tests use synthetic boxes.
- The enclosure audit casts rays that count either side of a surface (`:634`), so it can't detect inverted or backface-culled faces. The capture validator only accepts orthographic six-view batches (`validate_building_gallery_capture.ts:45`). Free perspective angles, low pitch and the 2.2-unit camera pull-in at `world.ts:195` remain visually unvalidated. To its credit, the validator records `manualApprovalClaim:false`.
- Footings only apply to props with a foundation anchor (`world.ts:142`, `terraces&&foundation`). This is not a comprehensive terrain repair, and none of this establishes full game parity.
