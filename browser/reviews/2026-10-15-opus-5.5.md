# Read-only review: browser HeartGold 3D port (rendering pipeline and field state)

**Before you read:** the working tree changed while I was reviewing. `render-repair.ts` went from 311 to 341 lines: a new `rockVolume` function appeared and `closeBuildingBack` changed how it picks the front. `world.ts` also changed, so the rear-wall code now combines warps from every nearby map header. Line numbers below match my last read. I did not run any tests or open the browser.

## Prioritized findings

### A. Rendering problems that affect the whole pipeline

**1. The surfaces added behind scenery ignore texture transparency, which explains the black rectangles around cliff rocks.** *Code: confirmed. Visual: strongly supported, not yet screenshotted.*
- **Rear backing on props:** `closeComponent` (`render-repair.ts:51-90`) builds the solid backing, the convex outline and the extruded sides from whole triangles. It never checks `alphaTest`/`transparent`. Wherever a cutout texture is see-through, you see a solid block of averaged colour behind it.
- **Cliff skirts on landscapes:** `closeTerrain` (`:254-269`) hangs a skirt from every open edge down to the lowest point of that piece. For a standing or leaning cutout card, the skirt from its top edge lies almost in the card's own plane. The polygon offset pushes it just behind the card, so it shows through every transparent pixel as a rectangle.
- **This happens on real data.** Route 29's landscape `land/2-2.glb` uses `allpeak` and `allpeak_p`, both `alphaMode:"MASK"`, and both match the terrain name filter `/peak/`.
- **Fix:** don't build backing or skirts from cutout or blended triangles. If closure is still wanted there, trace the outline from the texture's alpha inside each triangle's UVs. Skip top-edge skirts that are nearly in the card's plane.

**2. The tree-trunk detector splits single trees into several billboards.** *Confirmed from the data.*
- `export_foliage.py:31-37` finds "trunks" as solid runs along the bottom row of each texture. A single tree whose roots leave a gap counts as several.
- `foliage.json` shows this on single-tree textures: `en_tree02`–`05` → `[0.39, 0.60]`, `t_tree2_*` → about `[0.42, 0.62]`, `bf_tree01_*` → `[0.29, 0.46]`.
- Their repeated `_re` versions get 4 centres, for example `en_tree02_re: [0.14, 0.35, 0.64, 0.85]`.
- `treePanels` (`render-repair.ts:297-300`) makes one full-texture billboard per centre. Unless both stems snap to the same ground-mark anchor and get deduplicated, the result is doubled, offset trees.
- **Fix:** count trees per repeat by comparing the repeated texture's width to the single-tree texture's width, or use the `_un` ground marks. Add a test that every non-`_re` entry has exactly one centre.

**3. Choosing a building's front from nearby warps is fragile, so the new rear wall can land on the wrong side or be skipped.** *Code: confirmed. Visual: not verified.*
- **Every warp counts as a door:** `world.ts:73-77,89` passes in all warps from every header in the 5×5 loaded area: route-edge warps, caves, neighbouring houses. Any warp within 0.6 tiles of a building's bounds counts as one of its entrances (`render-repair.ts:105`).
- **Ties go to the side:** the front is whichever bounding face is nearest the door (`:101-104`). A door in a corner column ties between side and front, and the stable sort picks the side. Roof overhangs push the result further towards the side.
- **Unrelated warps can cancel the wall:** any warp that lands on the opposite face suppresses the wall entirely (`:106`).
- **Results depend on where loading started:** the result depends on the area loaded at that moment and is never recalculated. Example: a gate whose second door sits in a cell just outside the window gets a wall over that real passage.
- **The source data already says which way doors face.** Door tiles are behaviour `0x69` (`TILE_BEHAVIOR_DOOR`). The browser only allows entering them while facing north (`terrain.ts:20`), so every door is on a south façade. The `WARP_ENTRANCE_*` and `WARP_*` behaviours also carry a direction.
- **Fix:** take the front from the warp tile's behaviour. Only count warps whose tile falls inside the building's blocked footprint. Make the result independent of the loaded area.
- **Hypothesis:** the wall only fills the height of the walls, so if the original model also lacks a rear roof slope, that area stays open.

**4. The browser draws scenery the DS camera never showed, which likely explains the floating forest strips and possibly the sea/sand seams.** *Positioning: confirmed. Link to these reports: hypothesis.*
- The DS loads only 2×2 map cells at a time (`map_load_manager.c` quadrant loading). The browser loads 5×5 (`world.ts:76-82`).
- Filler cells around the playable maps sit at real source heights: forest model 208, sea model 209 (which contains `sea_line02` with `BLEND`), and mountain model 210. Altitudes run from 1 to 36 in `matrices/0.json`; for example x=27, z=5 has altitude 26, which is 13 tiles up.
- The browser height (`altitude × 0.5` tiles) matches the source exactly (`CalcMapPosition`, `<<15`). These cells just weren't meant to be seen from a free camera.
- Filler sea at altitude 1–2 sitting next to playable sea at altitude 0 may produce the "double border stripes".
- **Fix:** treat header-0 filler cells as backdrop. Add skirts down to the neighbouring height, or fade them out, or limit them to an outer ring.

**5. Fences lose their original colours.** *Confirmed.* `solidFences` (`render-repair.ts:197-207`) replaces every `fence`/`saku` material with fixed white and grey-blue boxes at fixed heights. Wooden or other non-white fences lose their source art. **Fix:** sample the source texture's colours and take the heights from the card's alpha rows.

**6. The new, uncommitted `rockVolume` swaps original rock art for generated rocks.** *Confirmed in the current working tree.* It replaces original rock cutouts with flat-shaded 8-sided procedural shapes (`:226-250`). Its name filter (`rock|iwa|boulder`) doesn't match Route 29's `allpeak*` materials, so it doesn't fix item 1 there.

**7. All materials are forced double-sided.** *Confirmed.* `originalMaterial` sets `side: DoubleSide` on every material (`render-repair.ts:7`), discarding the DS face-culling setting. Cutout cards then show the same art mirrored on their backs, and the closure code can't tell deliberately one-sided surfaces apart. *How much this contributes to "thin" rocks is a hypothesis.*

**8. Fence, flower, rock and tree repairs assume triangles come in quad pairs.** *Confirmed as a fragility; impact not measured.* `solidFences:187`, `flowerVolume:215`, `rockVolume:231` and `treePanels:289` assume triangles `i` and `i+1` form one quad. A single stray triangle shifts every later pair. **Fix:** group triangles by shared edges first (the existing `components()` does this).

**9. Props are placed differently from the DS.** *Latent; no current impact.* The browser applies each prop's stored rotation and the cell's altitude (`world.ts:87-89`). The DS ignores the stored rotation and adds only x/z (`map_prop_manager.c:117-119, 186-212`). I checked the data: every exported rotation is zero, and no cell with props has a non-zero altitude. Match the DS anyway so this doesn't break later.

### B. Gameplay and state

**10. Warps trigger differently from the original.** *Confirmed against source.*
- **Browser:** walking onto any warp tile warps you immediately (`main.ts:102-106`).
- **Warps that trigger on stepping:** in the source this only happens for north entrances, warp panels, ladders down and escalators (`field_control.c:703-748`).
- **Doors:** walking into a door you are facing triggers it (`:520-527`).
- **East/west/south exits and stairs:** you must stand on the tile and push in that direction (`:529-573`).
- **Order of checks:** the source checks coordinate events before transitions (`:647-651`); the browser checks them after.
- **Effects:**
  - Walking sideways across an exit mat or a gate-edge tile warps you.
  - After arriving, pushing down on the mat does nothing; you have to step off and back on.
- **Fix:** port this split and add push-to-warp in `step()` when the target tile is blocked.

**11. Crossing into a connected map runs scripts it shouldn't, and battles skip one they should.** *Confirmed against source.*
- The connection path runs `OnTransition`, `OnResume` and `OnLoad` (`main.ts:88`).
- In the source, `OnTransition` runs for both warps and connections (`field_warp_tasks.c:257-270`). `OnLoad` and `OnResume` only run when the field map is rebuilt, i.e. after a warp or after returning from a battle or menu (`fieldmap.c:189,213`).
- The browser never runs `OnResume` after a battle.
- 95 headers define `OnResume`, including New Bark (`scr_seq_T20_009` moves the friend and Marill with `MovePersonFacing`) and Route 22.

**12. Ledges are walls.** *Already acknowledged as incomplete, but it blocks play.*
- Ledge tiles (behaviours 56–59) carry the collision bit in 126 land files.
- `permissionWalkable` (`terrain.ts:4-9`) blocks them from every direction, so shortcuts and any ledge-only path are impassable.
- **Fix:** if the facing tile is a jump tile pointing the way the player faces, move 2 tiles with an arc, landing at the terrain height.

**13. Smaller divergences.**
- **Wild encounters:** they only check behaviours 2, 3 and 8 (`main.ts:114`). The source encounter list also includes 5, 11, 37, 114, 119, 123, 166 and 167 (`metatile_behavior.c`). Walkable tiles of the later group exist in lands 426 and 427, so encounters are missing there.
- **Toxic damage:** it does a flat 1/8 every turn (`battle.ts:84`) instead of growing each turn. `PARITY.md` lists this as Implemented.
- **Blackout spawn:** it is also updated on connections (`main.ts:87`). The source only does this on non-connection entries; no practical effect today because the spawn maps are interiors.
- **Streaming:**
  - Loading new cells is awaited inside the walking lock (`main.ts:143`), so steps can hitch at cell boundaries.
  - Scripted player movement never loads cells or updates the current map header. *Hypothesis:* a long scripted walk could leave the loaded area.

## Root cause

Each repair works out what an object is (building, rock, fence, tree, its front) from material-name patterns, triangle order and bounding boxes, one repair at a time. None of them know about:
- texture transparency or the DS material flags (face culling, polygon alpha);
- the map's own meaning: tile behaviours, door directions, footprints.

The DS assets were built for a fixed camera that looks one way and only ever has 2×2 cells loaded. Every new viewing angle exposes a guess.

**Recommendation:** have the exporter write a per-asset description that includes, at minimum:
- material alpha mode and cull mode;
- each prop's footprint and door direction, taken from the permissions and warp behaviours;
- trunk counts verified against the single-tree textures;
- whether each cell is filler.

The runtime repairs then read that description instead of guessing.

## Suggested checks
- **Data tests:** every non-`_re` foliage entry has one centre; repeated entries are a multiple of their single-tree count; list filler cells that sit at a different height from an adjacent playable cell.
- **Geometry tests:** a cutout quad gets no backing or skirt that lies in its own plane; for `closeBuildingBack`, cover a corner door with a roof overhang, an unrelated warp just behind the building, a gate whose second door is outside the loaded area, and the same building loaded from different centres giving the same result.
- **Field fixtures:** push south on an interior mat to exit; walking sideways across a 2-wide mat does not warp; crossing Route 29 into New Bark runs only `OnTransition`; returning from a battle runs `OnResume`; a ledge jump.
- **Browser check (QA save only):** using `__HG3D__`, orbit 8 yaw angles × 3 pitches at the Route 29 cliffs, the New Bark coast, the Cherrygrove Center and fences elsewhere. Log the loaded cells' altitudes alongside the screenshots.

## Implementation follow-up

Confirmed by direct browser rendering: coast black rectangles were caused by generated textured skirt geometry missing the colour attribute required by its material. The broader rectangular cut-out silhouette concern remains relevant for additional hill families. The current rock implementation now wraps original pixel art over closed geometry, superseding the untextured intermediate implementation seen by the reviewer.

Implemented after the review: canonical forked-root grouping; complete-matrix source entrance direction metadata; matrix forest foundations plus native raised forest-platform sides; native sand/shallow shore substrate. The full imported-geometry audit now retains real material flags and rejects enabled vertex colours without data. Review findings about non-white fences, quad pairing, other hill cutouts and gameplay/state parity are still open. Prop-rotation differences have no current data impact; double-sided paper artwork is intentional, while solid structure completeness requires independent geometry checks.
